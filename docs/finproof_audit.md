## 四、技术冲突（说明书 vs 当前项目可运行性）

按任务约定：**当完整产品方案与当前项目冲突时，以当前项目可运行性和 MVP 目标为优先。** 以下冲突均以"说明书怎么建议 → 冲突点 → 本项目决策"呈现。

| # | 说明书建议 | 冲突点 | 本项目决策 |
| - | ---------- | ------ | ---------- |
| 1 | 后端数据库用 **MySQL**，任务队列用 **Celery** | 仓库无任何数据库/消息队列基础设施；本地可运行性优先 | **SQLite（Python 内置驱动，零配置）** + SQLAlchemy 数据访问层；换 MySQL 只需改连接串。**不引入 Celery**，MVP 用同步任务（FastAPI 同步端点 / `BackgroundTasks`），单机单进程即可跑通全流程 |
| 2 | 大模型参与主张提取与证据理解（未指明模型与密钥） | 仓库无任何 API key / 环境变量假设；评委演示不能依赖外网模型 | 采用**混合核验架构**（见 6.5）：数字格式化 / 单位币种 / 同比环比 / 累计转单季 / 比率 / 差异比较 / 计算记录全部由**确定性程序**负责；主张拆解 / 语义识别 / 证据支持关系 / 因果与预测检测 / 修订建议由**大模型**负责；无 API Key 时走明确标识的 **Mock 模式**（`FINPROOF_LLM_MODE=mock`），Mock 结果不得伪装为真实模型结果 |
| 3 | 检索含 Embedding 语义检索 + Reranker | 无向量库 / Embedding 服务假设 | MVP 用**关键词 + 财务指标精确匹配 + 页码扫描**（说明书第十一节亦认可黑客松不需要大型向量库）；语义检索列为 P1 |
| 4 | 输入模式二"报告 + 公司名自动搜索公开来源" | 依赖交易所/官网数据源与爬虫，与 MVP"不包含大规模爬虫"边界冲突 | MVP 只做**模式一（报告 + 证据包上传）**，最稳定、最容易演示 |
| 5 | 测试集 FinProof-200（10 家公司 / 20 份报告 / 200 条主张） | 规模对黑客松过大，且当前 `data/` 无任何数据 | MVP 采用 **1 家真实上市公司 + 1 份真实年报 + 1 份预埋错误研报 + 20~30 条金标准主张**；金标准 JSON 结构按可扩展设计 |
| 6 | 功能七"可信版本自动修复"（生成修订后报告全文） | MVP 不包含自动发布，且修订生成依赖 LLM | MVP 只输出**修改建议文本**（写入判定理由）；修订版全文生成列为 P1 |
| 7 | 核验结果含第 6 类"属于观点或预测" | 任务书明确要求五类结果（支持/反驳/部分支持/证据不足/无法判断） | MVP 采用任务书五类；识别为观点/预测的主张归入"无法判断"并注明类型，观点标签列为 P1 |

> 补充说明：说明书第九节架构图（Next.js → FastAPI → 各引擎层 → MySQL）与本书推荐架构在**分层思想上完全一致**，仅数据库与任务队列两处为可运行性让步，不构成结构性冲突。

## 五、主要风险

| # | 风险 | 等级 | 说明与缓解 |
| - | ---- | ---- | ---------- |
| 1 | **PDF 表格/扫描解析不稳定** | 高 | 说明书自身已提示（风险一）。缓解：MVP 只支持文本型 PDF；演示文件在 Phase 1 预处理校验（能提取出文本才入库）；表格按页面文本块保存，不做复杂表格结构还原（P1）；不做 OCR |
| 2 | **误报过多**（把正确内容判错） | 高 | 缓解：五类判定含"无法判断"兜底；计算容差（四舍五入、亿元/万元写法、百分比精度）；金标准**同时包含错误与正确主张样本**，用误报率约束"发现错误"的冲动 |
| 3 | **演示数据可信度不足** | 高 | 财务数字必须来自真实披露文件（下载真实年报 PDF），预埋错误必须逐条记录金标准（错误类型、预埋值、正确值、理由），防止"自编数据"被评委识破 |
| 4 | **LLM 依赖导致演示失败** | 中 | 混合架构兜底：数字与计算全确定性；语义任务走明确标识的 Mock 模式（金标准/人工标注回放），Mock 结果不伪装为真实模型输出（见 6.5） |
| 5 | **范围蔓延** | 中 | 严格执行 `finproof_mvp_scope.md` 边界清单；说明书 P1/P2 项一律不进 MVP |
| 6 | **仓库无版本管理** | 中 | Phase 0 第一件事 `git init`；每阶段验收后提交 |
| 7 | **数据缺口：真实财报 PDF 获取** | 中 | 需在 Phase 1 前从巨潮资讯等公开渠道下载目标公司文本型年报；若目标公司 PDF 为扫描件则立即换公司（选披露结构标准、文件为文本型的大盘股） |
| 8 | **评测口径失真** | 中 | 金标准必须含：预埋错误主张（测错误召回率）+ 正确主张（测误报率）+ 证据不足主张（测拒答准确率），三类缺一不可 |
| 9 | **前端工程量挤占核验引擎时间** | 中 | 前端只做 4 个页面（上传/总览/主张列表/三栏详情），不做说明书中的证据链图谱与 diff 对照页（P1） |

### 6.3 数据流（单次核验流水线）

```text
上传研报 + 证据 PDF（POST /api/uploads）
  → 解析：按页提取文本，页码入库（documents / pages）
  → 提取：规则引擎抽取数字型主张（claims）
  → 结构化：数字/指标/期间/单位/币种归一化（claims 字段）
  → 匹配：指标关键词 + 数值匹配 → 证据段落与页码（evidence）
  → 计算：确定性引擎重算（同比 / 累计转单季 / 单位币种转换）（calculations）
  → 判定：五类结果（verifications）
  → 评分：FinProof Score 与分类计数（audit_runs）
  → 导出：JSON / HTML 审计报告（export）
```

### 6.4 与说明书架构的对应关系

说明书第九节推荐的"FastAPI 接口层 → 任务编排与状态机 → 文档解析层 → 主张提取层 → 证据检索层 → 财务规则与计算引擎 → 语义核验与矛盾检测 → 风险评分与报告生成 → 存储"与本架构一一对应，仅：

- 存储层 MySQL → SQLite（可运行性优先）；
- 任务编排 Celery → 同步流水线（显式函数调用链，天然就是说明书要求的"显式状态机"）；
- 语义核验中的 LLM 部分 → 混合架构（见 6.5）：语义类任务由大模型负责，无 Key 时走明确标识的 Mock 模式；
- 检索中的 Embedding → 关键词 + 指标精确匹配。

结论：**无结构性架构冲突，决策均为可运行性让步。**

### 6.5 混合核验架构原则（2026-07-31 修订）

FinProof 不是纯规则系统，也不是完全依赖大模型的系统，而是**混合核验架构**。

**确定性程序负责**（可重复、可测试、可解释）：

- 数字格式标准化；
- 单位和币种处理；
- 同比增长率 / 环比增长率计算；
- 累计数据转单季度数据；
