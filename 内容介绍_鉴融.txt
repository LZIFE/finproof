鉴融（FinProof）· 商业分析报告核验专家 · 产品详细介绍

版本：v2.1.0
定位：一款面向「商业分析报告」的事实核验 Agent——把 AI 写出来的报告，逐条找出数字错误、口径混淆、引用失当与逻辑漏洞，给出可溯源、可复核、可点开原文核对的结论，并输出一份完全透明的分数。
本方撰写于 v2.1.0 交付之后，以下所有机制、公式、边界均以该版本为准。


=========================================================
一、为什么需要鉴融：写稿越快，事实风险越藏不住
=========================================================

大模型把研报、行业研究、尽调纪要的「写稿」从几天压缩到几分钟，却顺带批量生产了事实错误、口径混淆与数字矛盾。成稿之后的「事实把关」成了新的瓶颈，而传统审稿几乎全靠人肉。

改进前，一份 30 页左右的深度研报，审稿人通常要——
· 逐页通读，手工圈出所有数字主张。一份报告动辄 30–60 个数据点
· 打开交易所公告、公司年报、Wind/Choice 终端，逐个核对原始披露。「报告期对齐、合并 vs 母公司、归母 vs 净利润、累计 vs 单季」这类口径，往往要反复翻 PDF 才能确认
· 用 Excel 手算复算同比增长、累计转单季、毛利率、业务占比，单个数字 2–5 分钟，一份报告仅复算就要 1–2 小时
· 遇到扫描件、图片表格，还得先 OCR 或手动转录，第一步就卡住
· 发现疑点后凭关键词搜几轮，搜不到就标「待核」，缺口无记录、不可追溯、下次重来

这套流程下，资深分析师审一份研报普遍需要【行业估算：2–4 小时】，且高度依赖个人经验——同一个口径坑，换个新人就可能漏掉。更棘手的是：AI 生成的稿量在涨，人工审稿产能没涨，质量只能靠「抽查」，漏检率随之上升。

鉴融要解决的，就是这道「写稿提速、把关没提速」的工序断层。它不替代分析师做判断，而是把机械、重复、需要精确复算的部分自动化，把真正需要人眼判断的剩余项，清晰、诚实地交回给用户。


=========================================================
二、鉴融是什么，不是什么
=========================================================

鉴融是「AI 写稿后的事实复审层」，不是「再写一篇报告的生成器」。

它的工作对象是一份已经成稿的报告 + 它所能取得的证据（用户上传的源文件，或联网可查的一手来源）。它把报告拆成可独立核验的结构化主张，用确定性计算引擎对照原始材料亲自复算数值，按八步决策链给出六类判定，并指出常见错误类型，最终输出一份可追溯的审计报告。

它明确不做的事——
· 不重写报告、不替你写结论、不生成「修订版」
· 不假装全能：核验不了的部分会分类、会交回，不会因为想给高分而把缺口说成通过
· 不伪装成多智能体编排、不伪装成向量库/语义检索、不伪装成它能访问它其实访问不了的私有数据
· 不编造来源、不编造链接、不把转述写成原文

一句话：鉴融是「事实守门员」，不是「代笔」。


=========================================================
三、核心能力全景
=========================================================

1. 主张自动拆解（Claim Decomposition）
   报告秒级拆为 30–60 条结构化主张，分为 A–G 七类：
   A 原始数字主张（直接陈述的财务/业务数值）
   B 计算型主张（含同比/环比/比率等推导）
   C 口径主张（单季/累计、归母/扣非、合并/母公司等）
   D 业务事实主张（定性业务结论）
   E 因果关系主张（归因型结论）
   F 比较型主张（同业/对标比较）
   G 预测和观点（前瞻/主观判断，不判真假的独立一类）
   每条标注类型、期间、口径、单位、币种与风险等级。

2. 确定性复算引擎（这是鉴融的硬核）
   对增长率、同比/环比、累计转单季、占比、毛利率、CAGR、ROE 等数字亲自复算。引擎用 Python decimal 精确十进制运算，单数字【引擎级：毫秒级】，并输出「公式 + 输入 + 与报告差异（含相对差%）」。
   容差（v2.1.0 实测确认值）：
   · 绝对数值 / 累计转单季：相对容差 0.1%（VALUE_TOLERANCE = 0.001）
   · 增长率：±0.5 个百分点（GROWTH_TOLERANCE_PP = 0.5）
   · 披露舍入豁免上限：0.5%（ROUNDING_EXEMPTION_CAP = 0.005），仅当差异可由声明的舍入精度解释时适用
   重要更正：早期版本文档写「容差 0.1%」，但代码长期停留在 0.5% 且未被发现——v2.1.0 之前的一次自查抓到这个 bug 并修复，0.1%–0.5% 区间的小幅偏差现在会被正确判为不匹配，而不是被放过。

3. 八步判定链
   每条主张依次经过：证据可用性 → 实体识别 → 指标对齐 → 期间对齐 → 口径对齐 → 数值核验 → 语义判断 → 结论映射，不跳过任何一步。来源是 backend 的 verdict_decision.py，专家在判定任意主张时都须遵循此顺序。

4. 六类结论（不是简单的「对/错」）
   支持 / 反驳 / 部分支持 / 证据不足 / 观点或预测 / 无法判断。
   其中「观点或预测」单独成类，不强行判真假，只核查是否披露了预测依据；「证据不足」与「无法判断」也明确区分——前者是「有材料但不够」，后者是「连判定的条件都不具备」。

5. 对抗性防御（专为「看起来对其实错」设计）
   真实造假与模型幻觉的主要形态不是「1.8 倍」那种明显错，而是「4.38 亿写成 4.6 亿（+5%）」落在容差内被放过。鉴融内置五类高危形态强制检查：
   · 容差内小幅篡改：数值类主张必须写出复算值/报告值/绝对差/相对差%，相对差 >2% 即便判支持也标 [微幅偏差]
   · 口径伪装：归母↔扣非、营收↔主营、单季↔累计、合并↔母公司，必须显式确认是否对齐
   · 单位与币种伪装：必须确认单位，存在 [单位未确认] 的条数要单列
   · 因果型当事实：归因结论须核对原始资料是否支持所引原因，仅事实成立不等于因果成立
   · 引用错配：来源/页码/期间不对齐要单独计数

6. 证据等级与「来源权威性」可计算
   证据分四档：S 级（监管/交易所/公司法定披露，权威最高）、A 级（权威媒体/第三方研报/政府统计）、其他（一般来源，给 40 分）、未注明（无来源，给 0 分）。
   这是 v2.1.0 才补齐的关键定义——早期版本只有 S/A 两档，「来源权威性」这一评分维度实质无法计算；现在四档齐备，该维度第一次可量化。

7. G1–G4 缺口分类与用户自核清单
   最终仍无法核验的主张，按 G1 源文件缺失 / G2 检索不可达 / G3 非公开数据 / G4 提取失败 分类，并在审计末尾汇总为「需用户自行核验清单」，按影响核心结论的程度排序。绝不把「核验不了」伪装成「通过了」。

8. 评分完全透明（详见第五、六节）

9. 来源可核对（详见第六节）——每条结论挂 [E##] 编号，点开即见原文

10. 内置 OCR
    扫描件、图片表格、乱码 PDF 由专家自己识别（pdf 文本直抽 → 渲染 → tesseract 中文 OCR → 多模态视觉核对，结果交叉验证），不再甩回用户。注意：这是 v2.1.0 的实际能力，早期版本文档里曾错误写「禁止假装支持扫描件/OCR（未实现）」，属包内矛盾，已修正。

11. 联网核验 + 聚焦再搜索
    联网模式下零配置调用 WorkBuddy 内置 WebSearch/WebFetch，对照一手来源自动交叉验证；首轮补证仍有缺口的主张，自动换词（全称/简称/代码/英文品名）、换源（年报原文→IR→权威媒体→行业库）再搜 2–3 轮，穷尽才保留「证据不足」。
    硬性约束（v2.1.0）：单次核验联网检索总量上限 40 次，超出则输出「未检索清单」并声明「未闭环 ≠ 通过」，不得静默少搜；预算优先分配给高风险主张。


=========================================================
四、工作原理：六步核验流水线
=========================================================

① 受理与结构识别
   用户给：报告文本 + 证据来源（报告+证据包，或 报告+公司名+基准日）。
   先定范围：本地模式（仅按上传内容，不联网）还是联网模式（+ 内置 WebSearch/WebFetch）。由用户决定，不由专家自定；表述不清时只问一次，未确认前绝不联网。

② 主张提取与分类
   拆成 A–G 七类结构化主张，标风险等级。主张数 >25 条时进入分批审协议：先出「审查计划」（总条数、分批方案、预计轮次），再分批输出，每批标进度，未审完不得给总分。

③ 证据比对与复算
   对照原始披露，按复算引擎公式亲自复算；无 shell 时引擎不可用，复算退化为模型内算——此时必须逐条标注〔心算估算，未经引擎复算〕，不得以相同置信度输出。

④ 八步判定链
   证据 → 实体 → 指标 → 期间 → 口径 → 数值 → 语义 → 映射。

⑤ 需求判定门 + 联网补证（按需）
   本地够 → 跳过联网；缺口确需外部数据 → 联网/聚焦再搜索补证，受 40 次预算约束。

⑥ 审计输出
   六段报告（见第六节）：报告基本信息 + 健康度（含评分推导）+ 证据清单 + 主张卡 + 自核清单 + 对抗性抽查 + 审计轨迹。

一条贯穿全程的纪律（v2.1.0 新增）：边查边记来源。检索或读文件时就要把 URL、时间、页码、原文片段记下来，事后补记必然遗漏或失真——这是整套「来源可核对」的前提。


=========================================================
五、分数怎么算：FinProof Score 完全公开
=========================================================

FinProof Score 是 0–100 的报告级健康度评分，五维加权，每条扣分必须可追溯到具体主张与证据编号。

五维与权重
   证据覆盖率        25%
   数字与计算准确性  25%
   引用一致性        20%
   来源权威性        15%
   时间与口径一致性  15%

统计口径（先定义分子分母，否则分数不可复算）
   N_d = 可判主张数 = 总主张数 − G 类（观点/预测不进分母）
   N_c = 已闭环主张数（拿到可核对证据）
   N_v = 数值类主张数
   E_v = 数值类错误数（复算不匹配）
   E_q = 引用错配数
   E_p = 期间问题数
   E_s = 口径问题数
   注：纯定性报告 N_v = 0 时，数字准确性按 80 兜底（设计约定值，非测量值，对外须注明）。

五维得分公式（惩罚系数统一为 2）
   证据覆盖率      = N_c / N_d × 100
   数字准确性      = max(0, 100 − E_v / N_v × 100 × 2)        （N_v=0 时取 80 兜底）
   引用一致性      = max(0, 100 − E_q / N_d × 100 × 2)
   来源权威性      = 已闭环主张的证据等级分均值（S=100 / A=70 / 其他=40 / 未注明=0）
   时间与口径一致性 = max(0, 100 − (E_p + E_s) / N_d × 100 × 2)

总分 = 0.25×覆盖率 + 0.25×准确性 + 0.20×引用 + 0.15×权威 + 0.15×时间口径，四舍五入到整数。

档位
   优（≥90）：须点名所有反驳/部分支持项，不能只报分
   良（75–89）：须列前三大问题
   一般（60–74）：须给整改优先级
   差（<60）：不建议直接采用，须逐条复核

主张级风险分（另一条独立分数）
   基准分 90 + 重要性调整（最高 +8） + 置信背离（(1−置信度)×24） + 口径背离（(1−口径对齐度)×12） + 预测背离（如有），clamp 到 [80, 100]；等级 LOW/MEDIUM/HIGH 由引擎输出，CRITICAL 为「引擎分≥90 且 该主张是核心结论承重依据」的联合判定，必须写理由。

诚实披露：重算前后的分数
   旧版分数是经验打分、不可复算。按新公式重算同一批数据——
   · 某 A 股研报：【实测】旧 89 → 新 86（良），因为重算后把「数值错误」与「口径问题」各自计入了对应维度
   · 某拟港股 IPO 简报：【实测】旧 94 → 新 95（优），但必须点名其中 1 条反驳项
   这两个重算结果都用独立脚本复算校验过，数字自洽。94/100 与 100% 覆盖率均为【自查口径，非第三方评测】——对外须主动声明。

报告中的分数不是「给个分」，而是完整推导链：统计口径构成（含对应主张编号）→ 五维明细（公式→观测→得分→加权）→ 证据等级分布（逐条对应证据编号）→ 扣分清单（序号·主张编号·证据编号·错误类型·依据·影响维度）→ 档位 → 公式来源 → 自评声明（声明这是自评、非第三方认证、可复算）。


=========================================================
六、审计报告长什么样：每条结论都能点开原文
=========================================================

固定六段结构
   零  报告基本信息
   一  报告级健康度（FinProof Score，完整推导）
   二  证据清单（Evidence Register）——所有来源集中在这里
   三  逐条主张核验卡——每条都引用 [E##]
   四  需用户自行核验清单（按影响度排序）
   五  对抗性抽查
   六  审计轨迹

二、证据清单：八字段，一个都不许少
   编号         [E01]…（按首次出现顺序，全篇一致）
   证据等级     S 级 / A 级 / 其他 / 未注明
   类型         本地文件 / 联网来源
   来源名称     具体到文件或机构，不许只写「公司公告」
   链接         联网必须给完整可访问 URL；本地文件写文件名
   抓取时间     YYYY-MM-DD HH:MM（实时数据还要另标数据时点）
   定位         页码 / 章节 / 表格名 / 段落序号
   逐字摘录     原文片段，用「」包裹
   关联主张     支撑或反驳哪些 #N

   样例：
   [E03] S 级 · 联网来源
     来源：某公司 2026 年第一季度报告（交易所信息披露平台）
     链接：https://example.com/disclosure/detail?id=xxxxx
     抓取：2026-09-10 17:22
     定位：第 3 页「主要会计数据」表第 2 行
     摘录：「营业收入 60.00 亿元，本报告期比上年同期增减 12.40%」
     关联：支撑 #3

三、主张卡：三条硬规则
   · 每条主张都必须挂 [E##] 编号——没有可核对来源的结论，不配写进报告
   · 摘录必须逐字，不得转述、不得改动单位或正负号
   · 取不到链接就如实写原因，不许留空、不许编造 URL

四、分数在报告里说明清楚（见第五节推导链）

禁止事项（违反即视为报告不合格）
   · 编造 URL、页码或摘录
   · 把转述写成「摘录」
   · 摘录时修改单位、正负号或数值
   · 无来源却写「据公开资料」而不标「未注明来源」档
   · 只给结论不给证据编号
   · 只列有利证据、隐去冲突证据
   · 把「付费墙没检索」说成「已检索未找到」

一份完整算例（模板内置，可独立复算）
   9 条主张 → 统计口径：可判 6 条、闭环 5 条、未闭环 1 条（证据不足）、数值类 4 条、数值错误 1 条、口径问题 1 条。
   维度         公式                      原始观测          得分    加权
   证据覆盖率   N_c/N_d×100               5/6              83.3   20.83
   数字准确性   100−E_v/N_v×100×2         100−(1/4×200)    50.0   12.50
   引用一致性   100−E_q/N_d×100×2         100−0            100.0  20.00
   来源权威性   闭环等级分均值            (3×100+70+40)/5   82.0   12.30
   时间口径     100−(E_p+E_s)/N_d×100×2   100−(1/6×200)    66.7   10.00
                                                     合计 75.6333 ≈ 76（良）
   这个 76 分，你可以拿计算器逐行对上；对不上就是我们的实现有问题。


=========================================================
七、能力边界与诚实声明
=========================================================

鉴融不假装全能。以下明确写进专家包，作为能力边界：
   · 不假装支持它访问不了的私有数据库；联网只走 WorkBuddy 内置搜索，不谎称有付费终端
   · 不假装多智能体编排；它就是单 Agent 走八步链
   · 不假装自动生成修订版；它只给审计与建议
   · 不假装大模型「天然可靠」；凡模型内算（无 shell）都标〔心算估算，未经引擎复算〕
   · 不把「付费墙没检索」说成「已检索未找到」
   · 评分是自评、非第三方认证、可复算；不可横向比较不同专家的分数

这些边界不是缺陷清单，而是「可信」的一部分——一个会主动说明自己做不到什么的核验工具，比一个声称无所不能的工具更值得托付。


=========================================================
八、适用场景
=========================================================

鉴融面向一切以「事实准确性」为核心的商业分析报告，典型场景：
   · 行业研究与市场分析
   · 竞品分析与对标研究
   · 商业模式分析与公司深度研究
   · 投资尽调报告与商业计划书
   · 投资备忘录与财务分析
   · 上市公司研报（验证最深的场景）
尤其适合「用 AI 写完初稿后，需要快速做一次事实与数字把关」的环节。早期版本曾把定位放到「任意事实性报告」（含政策解读、学术综述），v2.1.0 收敛为商业分析报告——金融研报仍是最深场景，通用场景可用但财务公式优势会被稀释，这一点对外不掩饰。


=========================================================
九、怎么用
=========================================================

两种模式
   · 本地模式：你上传报告 + 证据包（源文件），鉴融只按你给的内容核验，不联网。适合涉密或证据已齐的报告。
   · 联网模式：你给报告 + 公司名/基准日，鉴融调用内置搜索补证。适合需要交叉验证一手来源的报告。

交付形态
   · 对话内：六段审计报告，主张卡可逐条展开
   · 每条主张挂 [E##]，证据清单集中可点开
   · 末尾 FinProof Score + 五维明细 + 自核清单

最低使用建议
   · 给足证据：你提供的源文件越全，覆盖率越高、分数越可信
   · 看自核清单：Score 再高，G1–G4 清单里的高影响项也要你亲眼看
   · 别只看总分：优（≥90）也必须点名反驳项，分数高不等于没问题


=========================================================
十、技术架构
=========================================================

鉴融以 WorkBuddy 专家包形态交付，结构如下（v2.1.0）：

插件根
   .codebuddy-plugin/plugin.json      声明 agents + skills
   agents/finproof-verifier.md        专家定义 + 强制加载 Skill 的指令
   skills/finproof-verification/
      SKILL.md                        自足操作手册（容差表、八步链、六类结论、对抗性必做项、评分公式、分批审协议、检索预算、引用规范索引）
      references/                     15 份方法论文档（主张分类、错误分类、六类结论与证据等级、八步判定链、复算引擎、架构流水线、证据检索门、风险治理、演示教训、评分规格、引用格式、审计报告模板、联网核验、对抗性盲区、主张提取提示词）
      bin/finproof_calc.py            确定性计算引擎（decimal 精确运算，30 项回归测试随包提供）
      bin/test_finproof_calc.py       引擎回归测试

关于「方法论是否被装载」的说明（这是 v2.1.0 修掉的最关键工程问题）
   早期版本把 66 KB 方法论文档放在插件根的 references/ 目录，但专家规范里「资源声明」只有 agents + skills，没有 references 字段——官方专家包也全部自包含，references/ 只在 Skill 内部出现。结果是方法论可能根本没被加载，专家退化成「描述得很专业」的提示词。
   v2.1.0 的处置：方法论整体迁入 skills/finproof-verification/，在 plugin.json 声明 skills 字段；新建 SKILL.md 作为自足手册（不读 references 也能执行）；agent MD 加强制指令「核验前必须先加载 Skill，加载失败如实告知，不得假装按方法论执行」。这是一次结构性修复，不是补丁。


=========================================================
十一、透明承诺：为什么可信
=========================================================

鉴融的「可信」建立在三层可检验之上：

第一层·评分透明
   五维公式、权重、容差、算例全部公开，任何分数都能按公式复算；旧分数不可复算的问题已在 v2.0.0 解决。

第二层·来源可核对
   每条结论挂 [E##]，点开即见原文摘录、链接、抓取时间、定位；编造来源即视为报告不合格。

第三层·缺口可见
   G1–G4 把「核验不了」分类交回，不伪装通过；检索预算超限输出未检索清单，不静默少搜。

三层都做，审计报告才「能被检验」；能被检验，才是可信的前提。我们对外主动声明：94/100 与 100% 覆盖率为自查口径、非第三方评测；若你按公开公式复算对不上，是我们的实现问题。


=========================================================
十二、版本演进（体现工程严谨，不掩饰走过的坑）
=========================================================

v1.5.0 通用化：从金融研报扩展到任意事实性报告，但留下若干未改干净的遗留（frontmatter 仍写「金融研报事实核验专家」、展示层仍写「五类结论」）。

一次对抗性自查（v1.5.x 之后）发现 16 项缺陷，最大的是：方法论可能根本没被装载；核心卖点挂在「可选」组件上无降级声明；maxTurns=50 与 30–60 主张矛盾；包内五处自相矛盾。

v2.0.0 结构性修复：方法论迁入 Skill 并强制加载；聚焦商业分析报告；评分完全透明化；实测抓到容差 bug（代码 0.5% 与文档 0.1% 不符）并修复为 0.1%；补齐证据等级四档使「来源权威性」可计算；补降级声明、检索预算、分批审协议。

v2.1.0 来源可核对：新增证据引用规范（八字段、禁止编造）；审计报告改为六段结构含证据清单与评分完整推导；边查边记来源纪律；版本校验 0 warning 后注册打包。

这条演进线的要点不是「一路完美」，而是「每发现一个坑就修一个坑，并把修的过程也写进文档」——这本身也是透明的一部分。


=========================================================
十三、一句话总结
=========================================================

鉴融不追求「看起来什么都能核」，而是追求「每一条结论都可追溯、每一个分数都可复算、每一个缺口都可行动」——在 AI 写稿时代，做一层可规模化的事实质检，让「写得快」和「写得准」不再二选一。

如需复核我们的分数：拿计算器按第五节公式走一遍，对不上就是我们的实现有问题。
